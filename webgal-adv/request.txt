一、剧情快
剧情块是一系列由文字、背景图片、音乐可能还有动画组成的多媒体内容。我希望你自主或参考D:\Datastruct\WebGAL-fork 仓库（https://docs.openwebgal.com/webgal-script/）的引擎，撰写符合整体风格的引擎，支持其大多数功能。我希望你可以帮助我 【简化】 我的开发流程，使得我可以通过一个图形化的便利的方式来管理总结构的流程图和相互跳转；使得可以以不那么严格的格式来撰写内容。
不那么严格指的是，可以省略一些元标记，使用更加自然语言化的方式进行判断。
例如：(缩进仅仅便于阅读，无实际影响)'''
\mem 春晌, 葬火
春晌：所以，在婉婉道来之后眼前的少女对葬火如是说道。
    “嘿，如果是你的话……”
    她又摇了摇头，想了好久，还是开了口——\
        “可以，帮我……”

    \b救救我，还有，救救她。好吗？

葬火：“——欸？诶诶？”
    似乎没有搞清楚意思的葬火往后退了两步。\
        “等下所以我还什么都不知道啦……”
    \b她没有搞明白的是，为何这位看上去如此阳光的学妹，会说出如此令人毛骨悚然的话来。\
        不应该是这样的…吧。
    \b“魔法少女”，为什么会是这样的事情呢？

：春晌跑走了。
\mem 葬火
葬火要追问的问题都没有说完。
葬火：“所以……”
    先和知夏聊聊吧……

'''
这样的一段中的可以被识别如下：
春晌大块中的每一个以左引号开头的对话行交给春晌，其余行交给旁白。葬火块同理。
\当孤立于行尾的时候，符号代表它的下一行和这一行处于一个语块中，仅仅是一次换行罢了。如果这一符号不存在，则它的后文便会和上一行之间从属于两条对话，分别判定。
\“或者\"都是转这一引号的义，使它不再代表对话，而是旁白中的引号其他用法。这一组合开头的行不视为对话开始/结束。
需要注意的是，如上文中这样的情况
`
似乎没有搞清楚意思的葬火往后退了两步。\
“等下所以我还什么都不知道啦……”
`
会被视为一整段都是葬火的语言，走对话的模式。只要一条对话中有其中一行由未转意的左引号开头，则这一条对话即标识为非旁白（除非，这个文字块的前文是 “：……”（换言之，整个文字块都是旁白）。
\b代表黑屏文字。
\mem表示显现立绘的对象。

在剧情块中放置背景图片/视频、立绘、音乐等资源的方式可以选择与原实现一样。
    \m bgm1.mp3 
    \bg bgt01.jpg
也是合理的。

'''

    2“不要！”;
}
\c1 （……）
    （……）
\c2 （……）
    （……）
\c
无论如何……
'''
的形式，但这种形式限于当这些选择枝仅仅影响这一个文件。对于影响更大的，则我在第二节指出。

二、选项与流程图
选项的另一种方式是放在一个文件中，该文件格式与上述内容完全一致（换言之，它是一个剧情块集合的子集）
'''
（……）
\c{
    __LOCK 1“好的！”;      //必须是数字，否则将难以区分。
    2“不要！”;
    （……）
    n“……”
}
\c1 （……）
    （……）
\c2 （……）
    （……）
（……）
\cn （……）
    （……）
\c
（……）
'''
其中n指的是一个具体的数。

可以接受这样的可选格式：
a.根本没有\c1后的所有内容；
b.没有结尾的\c及后续内容，这时从最后一个\cn标识到结尾都属于最后一个选项。
c.甚至只是这样也可以——
\c{
    1“好的！”;
    2“不要！”;
    （……）
    n“……”
}
我们要求使用扩展名来区分游戏块、剧情文本块和剧情块内的选择枝。
扩展名分别为：.gmf,.txt,.chos。
所有的bgm，立绘、背景图片等资源放在单独的文件夹内（与webgal规范相同），
视频资源如果作为前台播放，则既可以扁平放在主文件夹中，也可以放到video文件夹中如规范称。

再说上面的图形化编辑流程图方式。
我的开发框架很可能是一个工作文件夹内放置许多txt文本和游戏块文件与选项块文件。
流程以一个独立的文本形式储存在工作区的首页，可以通过你即将编写的一个图形化入口来打开、查看和编辑。
文件内容例如：
'''
@XU.CONTINUE-A:           //文件头。指出起点是XU文件里的CONTINUE-A标签结算。
->video1.mp4
->dialog1(.txt)   //.txt,.chos后缀可以省略。如果前名相同的.txt,.chos,.gmf全部出现，将优先语法上视为.txt，.chos和.gmf。
    \m bgm1.mp3 
    \bg bgt01.jpg
->dialog2       <x       //x是一个代号，代表本行内容，语法请参考c语言的goto。<x前可以有空格，也可以没有（<不是合法的文件名，所以可以区分），但推荐有。
->dialog3           
    \m bgm2.mp3
->ch1{
1:  ->dialog10
    ->dialog11
        \m bgm3.mp3
    ->ed1;         //分号可选。
2:  ->dialog20
    ->dialog21 <y
        \m bgm4.mp3
        \bg bgt02.jpg
    ->bt01-b{'w':->;'l':->;}
    ->dialog22
    \bg NONE
    if(time(x)==1) tagA=1;   (不以->开头，即意味着不是一个名词性短语：只能是控制语句，或变量标记语句。)
    ->(time(x)<=3)?x:ed1;   //三元运算符。提供几个运算功能和内置方法，包括time()，代表这一标签已经出现了多少次。
3:  ->;            //代表走出大括号。
4:  ->dialog40
    ->y;
5:  ->dialog50
    ->RETRY;
}
->dialog31
    \m
->video2.mp4
->bt01{
    'w':->
    'l':->RETRY;
}
if (tagA){          //C的if-else语法。
    ->dialog00-A
    ->CONTINUE-A    //CONTINUE-N,代表未完结的尾tag。相当于一个return，后续便不会再读了。
} else{
    ->dialog00-B
    ->CONTINUE-B
}

->dialog-BE1     <ed1
->END

'''
以下字符会被识别为控制字符：
START（“开始”。该字符意味着这个剧情线不接续任何其他线路，是独立开端。）
CONTINUE-XXX（XXX为任意由阿拉伯数字、大小写字母、“-”、“_”、“+”、其他语言字符组成的字符串。
此字段代表读到这里后停止该文件的读，将被有"@MC1.CONTINUE-XXX:"的文件头的文件接续。）
END（结束）；
NONE（定义为无bgm等。）
RETRY（此字段代表将所在的分支源）
UNLOCK/LOCK（该方法有下）
UNLOCK@MC2（代表解锁MC2那个flow文件的内容。实现由它的上游确定（如在此处，是在剧情列表中解锁。））
LOCK@MC2（同理，锁定……的内容）
UNLOCK@chos1[1]（解锁选择枝。LOCK同理。）

bgm等如果无特殊说明，将默认延续，直到在某个小文件或者本时间轴文件中，其被结束。

如果有多个START，建议存在一个MAIN文件。
内部仅仅写默认起点文件名,如
'''
XU
'''
可以由调用方决定起始剧情到底用哪个（接口你自己定）.
另外地，一个文件可以同时在文件头标明多个CONTINUE/START:
@XU.CONTINUE-A||@SC1.CONTINUE-AR||START

三、游戏块

开头要写其遵从的规则。
本文中是
rule AUTOCOMBAT.
你会建立一个AUTOCOMBAT.rule文档处理规则接口问题。
后文由规则接口而定。
此规则提供后文的语法，包括：
要传入什么，
用什么语法传入，
到哪里去通过什么方式（注，其只能做到引导至某个可执行文件或者服务器api）处理数据和进行判断，
此方式中是否引起页面的变化，
最后以什么为返回值。
这里，请你的接口使其游戏块文件可以这样写：
'''
rule AUTOCOMBAT

set TEAMS:Y{Y5,Y60,Y7,Y8},X{Y9},Z{Y12};
set CONTROL:NONE;
set BIND:Y;
battle Y vs X KEEP_STATUS;
battle Y vs Z;
if (isAlive(Y)) return "w";
else return "l";

DISPLAY:AUTOCOMBAT_DEFAULT
'''
（具体实现可以略改善）。


四、最终实现
点击“剧情模式”后，进入“章节选择”。
玩家选择其中的一章，即进入这一章具体剧情。（测试：给出三个测试章节，其中第三章以第二章完成为前提，是它的continue后续）
在每一章中有放置音乐、立绘、背景以供测试，要有战斗实例的测试。
当到达游戏块的时候，弹出
“剧情战斗”框，框内分列双方角色卡和技能组。
点击开始战斗，进入战术室自由对战的界面，进行ai战斗。
战斗中，Y先同X作战，结束后再以当前状态同Z作战（按照上述我的示例来走）。
战斗结束后，依照胜负继续进行剧情。如果是负-retry，先提示再使之重试。
